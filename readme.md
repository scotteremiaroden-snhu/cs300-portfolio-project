Project Reflection

The problem addressed across both projects was designing and implementing a data management system for ABCU’s academic advising program: software that could load a file of Computer Science course records, print the full course list in alphanumeric order, and look up a single course along with its prerequisites. Project One required producing pseudocode for three candidate data structures, a vector, a hash table, and a binary search tree, along with a Big O analysis of the file-read and insertion operations for each, in order to recommend one for implementation. Project Two carried that recommendation into working C++ code.

My approach started from the advisors’ actual usage pattern rather than from the data in isolation. The course list for ABCU’s Computer Science program is small, currently eight courses, so understanding how each data structure behaves is more important than how it performs at this particular scale; the choice has to hold up as the dataset grows. Working through the runtime analysis made clear that the three structures trade their costs in different places: a vector appends in amortized O(1) but searches linearly; a binary search tree can print a sorted list in a single in-order traversal but is vulnerable to the order records arrive in; a hash table offers O(1) average lookup and insertion but carries no ordering of its own. Since the course file is already sorted by course number, a plain binary search tree would degenerate into a linked list on load, which ruled it out despite its appeal for the print-list requirement. Weighing the stated priority, that advisors look up individual courses more often than they print the full list, against that constraint led to the hash table recommendation, which Project Two implemented directly.

The main roadblock was less about syntax than about data integrity. Because the hash table has no ordering and because prerequisite references are stored as plain course number strings, there was no guarantee that a prerequisite listed on one course actually corresponded to a course present in the file. I addressed this by reading the file in two passes: the first pass parses every line and records the set of course numbers that actually exist, and the second pass inserts each course into the hash table while checking that its prerequisites are included in that set, printing a warning for any that are not. This caught malformed input without rejecting the entire load, which seemed like the more useful behavior for an advisor relying on the tool during a session with a student.

This project expanded how I think about data structure selection: picking one effectively means projecting how a structure’s theoretical runtime interacts with the actual shape and order of real input, not just comparing textbook Big O notation. The pre-sorted course file is a concrete example; its order looks harmless until it is traced through to the binary search tree’s insertion logic, which is exactly the inflection point where it becomes a liability.

It has also sharpened how I write maintainable code. Separating the hash table into its own class, keeping the hashing, trimming, and uppercase normalization as small single-purpose functions, and validating prerequisites in a distinct pass rather than inline during insertion all make the logic easier to follow and change later. A future developer, or myself returning to this code after some time away, should be able to locate the hashing function or the parsing logic without having to trace through the full menu loop to find it.
